<Callout type="important" title="The thesis">
Jump height is the most expressive input in a platformer, and it lives in a single button. Variable jump height turns how long you hold into how high you go. Without it, every obstacle in the game has to be designed around one arc.
</Callout>

<h2 id="what-is-variable-jump-height">What is variable jump height?</h2>

Variable jump height means the jump you get depends on how long you hold the button: release early and the character stops rising sooner. In my lab a tap gives a hop of 1.1 tiles and holding gives the full 3.6 tiles, with everything in between available. Super Mario Bros. already worked this way in 1985: hold A longer and Mario jumps higher.

The point isn't the two extremes. It's the continuum. The chart below is the same jump code with four different hold times, simulated with the lab's real numbers.

<h2 id="variable-jump-godot">How to code variable jump height in Godot 4</h2>

My lab does it with gravity. While the character rises with the button held, gravity is normal. The moment you release while still going up, gravity is multiplied by 3 until the jump peaks. The comments are in Spanish because the whole project is.

<CodeBlock filename="addons/platformer_kit/player/player.gd">
```gdscript
# SALTO VARIABLE: soltar el botón mientras se sube multiplica la gravedad.
# Toque corto = saltito; mantener = salto completo.
if _jumping and not _jump_cut and velocity.y < 0.0 and not jump_held \
		and _wall_jump_hold <= 0.0 and Lab.on(&"variable_jump"):
	_jump_cut = true
	jump_cut.emit()

var gravity: float
if velocity.y < 0.0:
	gravity = p.gravity_up
	if _jump_cut:
		gravity *= p.jump_cut_gravity_mult
```
</CodeBlock>

Two details in there matter more than the multiplier. The cut happens once per jump (`_jump_cut`), so pressing again mid-air doesn't undo it. And `_wall_jump_hold` blocks the cut for the first 220 ms of a wall jump: someone mashing the button against a wall would otherwise lose height on every kick.

<h2 id="three-ways">Three ways to do it, and how each one feels</h2>

There are three common recipes. They all make a tap shorter than a hold, and they feel different at the moment of release.

<Tabs labels={["Gravity cut (my lab)", "Sustained speed (Celeste)", "Velocity cut (naive)"]}>
<TabPanel>

Release while rising and gravity triples until the peak. The arc bends instead of breaking: the character still decelerates smoothly, it just does it faster. This is what the chart above shows.

</TabPanel>
<TabPanel>

Celeste turns it around. The jump starts at full speed, and for up to 0.2 s (`VarJumpTime = .2f`) holding the button keeps the upward speed from dropping. Let go, or run out of time, and normal gravity takes over.<Sidenote>From [Player.cs](https://github.com/NoelFB/Celeste/blob/master/Source/Player/Player.cs), the player code the Celeste team put on GitHub. C#, lightly trimmed.</Sidenote>

<CodeBlock filename="Celeste/Source/Player/Player.cs">
```csharp
//Variable Jumping
if (varJumpTimer > 0)
{
    if (AutoJump || Input.Jump.Check)
        Speed.Y = Math.Min(Speed.Y, varJumpSpeed);
    else
        varJumpTimer = 0;
}
```
</CodeBlock>

</TabPanel>
<TabPanel>

The version most tutorials start with: when the button comes up, multiply the upward speed by something like 0.5. It works, and you can see it work: the arc has a visible kink at the instant of release. This is a generic sketch, not code from my project.

<CodeBlock>
```gdscript
if Input.is_action_just_released("jump") and velocity.y < 0.0:
	velocity.y *= 0.5
```
</CodeBlock>

I picked the gravity cut because it keeps the arc continuous and has a single number to tune. Celeste's approach has a property of its own: for the first 0.2 s a held jump rises at a constant speed, so a held jump is easy to read.

<h2 id="when-to-use">When variable jump height helps, and when it doesn't</h2>

| Situation | Variable jump? |
|---|---|
| Action platformers with one jump button | Yes. Super Mario Bros. already did it in 1985. |
| Low ceilings, spikes overhead, tight tunnels | Yes. The short hop is the tool that solves them. |
| A game built around committed jumps | No. Castlevania (1986) gives Simon one fixed jump arc, and its levels are built around it. |
| Buffered jumps | Careful. If the button was already released when the buffered jump fires, it's cut on the first frame and comes out as a short hop. |

<Collapsible title="Why a 0 ms tap still gives 1.1 tiles">
The jump starts at full takeoff speed (758 px/s here) and the release is only checked once the character is already rising, so even the shortest tap gets a moment at that speed before gravity triples. That moment plus the tripled gravity is the 1.1-tile floor. If you want a lower minimum, the knob is `jump_cut_gravity_mult`, not the release timing.
</Collapsible>

<h2 id="quick-answers">Quick answers</h2>

<h3 id="short-hop-height">How short should a short hop be?</h3>

In my lab the shortest hop is about 30% of a full jump: 1.1 tiles against 3.6. Low enough to stay under the lab's three-tile spiked ceiling, long enough (2.5 tiles at a run) to clear a two-tile gap.

<h3 id="cut-velocity-or-gravity">Should I cut the velocity or raise the gravity?</h3>

Raise the gravity if you want the arc to stay smooth; cut the velocity if you want the release to be visible. Both work. The gravity version has one parameter, the multiplier (3 in my lab).

<h3 id="hold-window">How long should the hold window be?</h3>

Celeste caps it at 0.2 s. My lab lets the hold matter all the way to the peak, 0.38 s, because the cut can happen at any point while rising.

Go back to sheet 02, switch the technique off, and try to get under the ceiling. You'll start tapping the button harder, as if force could make the jump shorter. That reflex is the whole argument: players already believe the button works this way.
