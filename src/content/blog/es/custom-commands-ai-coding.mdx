El commit que movió este post a su URL actual también agregó `.claude/specs/improve-blogs.md`. Es un spec para seis componentes interactivos del blog: Tabs, Collapsible, InteractiveChart, MermaidDiagram, CopyableCommand y FileTree. Ese mismo commit trajo los seis, y cuatro aparecen en esta página. El spec sigue la plantilla de `/spec-create`, el primer comando de este post. Los comandos habían entrado al repo esa misma noche, un rato antes, en el mismo commit que el primer borrador de este post.

Al final del spec siguen cuatro preguntas abiertas, sin ninguna respuesta escrita debajo. El código las respondió; el archivo nunca se puso al día. Tenlo presente mientras te cuento lo disciplinado que es el pipeline.

La idea es vieja. El [desarrollo guiado por especificación](https://en.wikipedia.org/wiki/Specification-driven_development) consiste en decidir *qué* quieres antes de escribir *cómo*. Aplicarlo a agentes de código es más nuevo, y no todo el mundo está convencido. Birgitta Böckeler revisó Kiro, spec-kit y Tessl [para martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) y salió escéptica: los pasos y los markdown de spec-kit le parecieron "overkill for the size of the problem", y escribió que prefería revisar código antes que todos esos archivos markdown. Creo que tiene razón sobre el costo. Casi todas las reglas de mis comandos están ahí para mantener ese costo bajo.

El mecanismo es sencillo. En lugar de escribir las mismas instrucciones en cada sesión ("explora mi codebase primero", "sigue los patrones existentes", "los tests van en la misma fase que el código"), las escribes una vez como slash commands. Archivos markdown. Sin SDK, sin API, sin plugin.

## Por qué los prompts crudos fallan a escala

Cuando escribes *"agrega autenticación JWT a mi API"*, le estás pidiendo al modelo que tome docenas de decisiones implícitas:

- ¿Qué librería de JWT?
- ¿Dónde se almacenan los tokens?
- ¿Cómo se integra con tu middleware existente?
- ¿Cuál es tu patrón de manejo de errores?

El modelo va a adivinar. A veces acierta. A menudo no. Y terminas gastando más tiempo corrigiendo las suposiciones de la IA que lo que hubieras tardado escribiendo el código tú mismo.

<Callout type="important" title="La idea central">
El cuello de botella no es generar código, es la **especificación**. Si defines claramente *qué* quieres, el *cómo* se vuelve casi trivial para el modelo.
</Callout>

No tengo un número limpio de antes y después para esto. Una versión anterior de este post traía una gráfica de retrabajo; la quité porque nada la había medido. La evidencia más cercana que tengo llegó después: cuando corrí `/insights` sobre un mes de sesiones con Claude Code en un side project, las features que arrancaron con un spec escrito terminaron más limpias que las que improvisé en el chat. Ese mes tiene [su propio post](/blog/es/tests-gave-me-control/).

## Comando 1: crear. De idea a spec estructurado

Le das un nombre y una descripción general. El comando escribe un spec estructurado en `.claude/specs/<nombre>.md` con contexto, comportamiento esperado, edge cases, lo que no debe hacer, restricciones, criterios de aceptación y, al final, las **preguntas abiertas** que detectó y que *tú* tienes que responder.

Este es el archivo real, recortado:

<CodeBlock filename=".claude/commands/spec-create.md">
```markdown
---
description: Crea un spec inicial en .claude/specs/ basado en un prompt simple
argument-hint: <nombre-feature> <descripcion breve>
allowed-tools: Read, Write, Bash(mkdir:*)
---

# Crear Spec Inicial

Quiero crear un spec para la feature: **$ARGUMENTS**

## Tu tarea

1. Crea el directorio `.claude/specs/` si no existe
2. Toma el input que te di y genera un spec estructurado
3. Guárdalo en `.claude/specs/<nombre-feature>.md`

<!-- plantilla recortada: contexto, qué quiero, comportamiento
     esperado, edge cases, lo que NO debe hacer, restricciones,
     criterios de aceptación, preguntas abiertas -->

4. Al terminar, dime el archivo creado y qué preguntas
   abiertas debería responder antes del siguiente paso

**No explores el código todavía. Solo crea el spec con lo que te di.**
```
</CodeBlock>

El frontmatter no está de adorno. `argument-hint` aparece en el autocompletado. `allowed-tools` lista las herramientas que Claude puede usar en ese turno sin pedirme permiso, así que crear la carpeta y escribir el archivo no se detiene a preguntar.

En lugar de adivinar qué librería de JWT prefieres, te pregunta.

<Callout type="tip" title="Adelanta las decisiones">
Una pregunta resuelta en el spec te cuesta una oración. La misma pregunta resuelta por la adivinanza del modelo vuelve después en forma de código que tienes que leer, poner en duda y reescribir.
</Callout>

## Comando 2: auditar. El spec se encuentra con tu codebase

Aquí el modelo explora tu proyecto real (estructura de archivos, convenciones de nombrado, manejo de errores, dependencias) y le agrega al spec un análisis técnico: archivos a modificar, archivos a crear, patrones a respetar, riesgos y las preguntas que todavía te toca responder.

<Collapsible title="Lo que explora el audit">

- Estructura del proyecto (carpetas, módulos, capas)
- Patrones de arquitectura (MVC, service layer, feature-based)
- Convenciones de nombrado de archivos y funciones
- Enfoque actual de manejo de errores
- Organización de los tests
- Dependencias en package.json / requirements.txt
- Archivos similares a lo que se quiere construir (para seguir el mismo patrón)

</Collapsible>

El audit corre con `context: fork` y `agent: Explore`, así que la exploración ocurre en un sub-agente aparte y a la sesión principal solo vuelven los hallazgos. Es el truco de aislar contexto que el [módulo de context engineering](/es/learn/agentic-systems/context-engineering/) recomienda para trabajo de solo lectura: una ventana limpia lee decenas de miles de tokens y tú te quedas solo con el resumen.

Este paso apunta a una falla concreta del código generado por IA: ignorar los patrones que el proyecto ya tiene. Después del audit, el modelo conoce tus convenciones y el código que escriba después encaja con ellas.

<Callout type="warning" title="Un bug en mi propio archivo">
Explore está documentado como un agente de solo lectura: Write y Edit están bloqueados. Mi `spec-audit.md` corre en Explore *y* le pide actualizar el archivo del spec. Esas dos instrucciones se pelean. Si copias este comando, deja el fork para explorar y que sea la sesión principal la que escriba el análisis en el spec, o quita `agent: Explore`.
</Callout>

## Comando 3: revisar. El semáforo de preparación

Antes de invertir tiempo en implementar, este comando evalúa el spec. Los emoji vienen tal cual del archivo del comando:

<Tabs labels={["Listo", "Con supuestos", "Bloqueante"]}>
<TabPanel>

🟢 Listo: bien definido. Todas las decisiones tomadas. Avanzar al plan.

</TabPanel>
<TabPanel>

🟡 Puede avanzar: hay ambigüedad, pero se pueden hacer suposiciones razonables. Cada supuesto se lista explícitamente para que lo apruebes o lo cambies.

</TabPanel>
<TabPanel>

🔴 Bloqueante: quedan decisiones críticas. Ejemplos: "¿Sesiones o JWT?", "¿Qué base de datos?", "¿Necesita real-time?" Resuélvelas antes de continuar.

</TabPanel>
</Tabs>

Termina preguntándote si quieres ajustar algo, y el archivo le dice que no haga nada más hasta que respondas. Si algo está en rojo, lo arreglas ahora, no después de tres fases de implementación.

## Comando 4: planear. Implementación por fases

El comando de plan lee el spec ya auditado y genera un plan por fases. Cada fase es pequeña, verificable (con un criterio claro de "está listo") y revisable antes de que arranque la siguiente. Los tests van en la misma fase que el código. Este ejemplo es una composición del formato, no la salida de una corrida concreta:

<CodeBlock filename="Ejemplo de plan">
```markdown
### Fase 1: Schema y migración
**Objetivo:** La tabla Users existe con campos de auth
**Archivos:** crear migración, modificar schema
**Tests:** migración up/down
**Verificar:** la migración corre sin errores

### Fase 2: Middleware de auth y utilidades
**Objetivo:** Rutas protegidas retornan 401 sin auth
**Archivos:** crear middleware, crear utils, modificar entry
**Tests:** unit tests del middleware
**Verificar:** curl ruta libre → 200, protegida → 401
```
</CodeBlock>

<Callout type="warning" title="Máximo 3-4 fases">
La regla del archivo: máximo 3-4 fases para features medianas. Si necesita más, la feature es demasiado grande y hay que dividirla. Yo la he roto. El spec de GSAP de este repo, titulado "Full Site Enhancement", tiene cinco fases y 23 pasos numerados. Ese título nunca iba a describir una feature mediana.
</Callout>

El plan mode que trae Claude Code se solapa con este paso, y mi plan tiene el mismo límite: vive en el chat. `/spec-implement` lee "el plan que acordamos" de la conversación. Lo que sobrevive a la sesión es el archivo del spec, que queda commiteado junto al código.

## Comando 5: implementar. Una fase a la vez

El comando de implementación recibe el nombre de la feature y un número de fase (`/spec-implement auth-jwt 2`) y ejecuta solo esa fase. Si se topa con algo que cambia el plan, tiene que detenerse y avisarme antes de improvisar. Al cerrar cada fase corre los tests relevantes, resume los archivos que tocó y las decisiones que tomó, y me pide luz verde.

Eso es lo que lo separa de "generar todo de un golpe". Si la Fase 1 revela un problema, ajustas el plan antes de que arranque la Fase 2. Detrás hay matemática: los errores por paso se multiplican, y una [compuerta de verificación a mitad de la cadena](/blog/es/high-accuracy-agent-priorities/) convierte una corrida larga y frágil en tramos más cortos que reinician el error.

La compuerta solo sirve si de verdad lees lo que hay detrás. Aprobar resúmenes de fase sin mirarlos es el rubber-stamping contra el que advierte el [módulo de human-in-the-loop](/es/learn/agentic-systems/human-in-the-loop/).

## Bonus: comandos de review

Dos comandos más quedan fuera del pipeline, para revisar calidad de código cuando lo necesites:

| Comando | Qué revisa | Salida |
|---|---|---|
| Performance | Loops O(n²), queries N+1, memory leaks, caché, bundles | Hallazgos por severidad con fixes |
| Arquitectura | SOLID, acoplamiento, separación de responsabilidades, seguridad | Diagrama de capas + roadmap de refactor |

Claude Code [fusionó los custom commands con las skills](https://code.claude.com/docs/en/slash-commands). Un archivo en `.claude/commands/spec-create.md` y una skill en `.claude/skills/spec-create/SKILL.md` crean el mismo `/spec-create`, y los archivos de comandos viejos siguen funcionando. La documentación dice que para lo nuevo es mejor una skill, porque puede llevar archivos de apoyo. Además, Claude puede cargar una skill por su cuenta cuando le parece relevante.

Esa segunda parte es justo la que conviene apagar en este pipeline. Agrega `disable-model-invocation: true` al frontmatter de `spec-implement`, como mínimo (los archivos de comandos aceptan el mismo campo), para que la única forma de arrancar una fase sea que tú escribas el comando.

## La regla de oro

Mi README cierra el flujo de specs con una "regla de oro", y la mantengo tal cual:

> Nunca saltes pasos bajo presión. El tiempo que "ahorras" saltando el audit o el review lo pagas triple en correcciones después.

Sigo sin tener una respuesta limpia a la pregunta de Böckeler sobre para qué tamaño de problema sirve esto. Lo que tengo es un tope en `spec-plan.md`, un spec de GSAP en mi propio repo que se lo pasa por encima, y un spec para los componentes de esta página con sus preguntas abiertas todavía ahí, sin responder. Un spec vale la revisión solo mientras sea lo bastante chico como para que de verdad lo revises.
