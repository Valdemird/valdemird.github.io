This Saturday I had three Claude sessions running in parallel on a small Next.js side project. Each session was working on a different bug. By dinner I had merged three PRs.

That worked because of one thing: each Claude lived in its own git worktree. The first time I tried this without that discipline, my morning ended with Next.js compiling itself in a loop and me copying the error into a fresh Claude to figure out what had gone wrong. That was the lesson tax. This post is what I bought with it.

<Callout type="important" title="The thesis">
A git worktree isn't a productivity hack for humans. It's a file-level isolation boundary between agents. The moment you have two Claudes touching the same tree, you need one.
</Callout>

## Why two agents on one repo collide

I started out of impatience. I'd ask Claude to do something (a multi-file refactor, a phased hardening pass, anything that took more than a few minutes) and I'd sit there watching the tool calls scroll. After a while I started wondering if I could just open another terminal and start the next task in parallel. Two Claudes, two tasks, one me.

Doing it that way without thinking is dangerous. If both sessions share the same working tree, the second one is editing files the first one hasn't finished reasoning about. Or worse, the second one stashes changes from the first one because git looks at the index and sees uncommitted work.

Worktrees are how you make the same impulse safe. Each agent gets its own checkout, its own branch, its own working directory. They can't see each other's in-flight files. Two terminals, two trees, no collisions.

That's the clean story. The actual one starts with me breaking it.

## The first time it broke

The first time I asked Claude to create a worktree, it created the worktree *inside* the repo it was working in, right in the tree that Next.js was actively watching.

I didn't notice immediately. What I noticed was that `next dev` started compiling and never stopped. The spinner would tick, finish, restart. Tick, finish, restart. I couldn't load the app. I couldn't tell if my code was broken or if the dev server was broken or if my computer was on fire.

What was happening, once I figured it out, was almost comically simple. Next.js was watching the repo for changes. The worktree Claude had created contained a literal copy of the repo's source files, sitting *inside* the directory being watched. Every time Next.js finished a compile, the file watchers saw "new" files in the worktree (same content, different paths), kicked off another compile, finished it, saw the worktree files *again*, and the loop never ended. The repo was watching itself.

I copied the error stream into a fresh Claude session and Claude figured it out. The same tool that had put me in the hole helped me climb out. That part I won't pretend was elegant. The diagram is the loop as Claude and I pieced it together from that error stream. It simplifies how Next.js actually watches files.

<Callout type="warning" title="Where you put the worktree matters">
If your dev server uses file watchers (Next.js, Vite, Webpack, any HMR setup), the worktree must live outside the watched tree. The safest option is a sibling directory: `../worktree-name`, outside the repo entirely. Hidden subdirectories like `.claude/worktrees/` can work too, but you have to configure the watcher to ignore them. `.gitignore` alone won't, since most watchers don't read it. Inside the watched source root with no exclusion, you'll watch yourself recompile forever.
</Callout>

After that I changed two things. First, I told Claude in `CLAUDE.md` to place all worktrees under `.claude/worktrees/<branch-name>` and never inside the source tree. Second, I added that path to `.gitignore` so nothing accidental would end up in a commit.

Everything that follows happened because of that loop.

<Callout type="note" title="Update, Oct 2026">
When I wrote this I was setting up worktrees through `CLAUDE.md` rules. Claude Code already had a flag for it (`--worktree`, or `-w`, added in v2.1.49 in February 2026), and it uses the same path I'd picked: the command below creates `.claude/worktrees/fix-db-pool/` on a new branch called `worktree-fix-db-pool`.

<CopyableCommand command="claude --worktree fix-db-pool" />

A `.worktreeinclude` file at the repo root copies gitignored files like `.env` into each new worktree. As of v2.1.222 (August 2026), every kind of worktree session refuses edits and Bash commands that target the main checkout, including git redirected there with `git -C` or `GIT_DIR`. The details are in the [worktrees docs](https://code.claude.com/docs/en/worktrees). None of this changes where the dev server's watcher looks, so the warning above still applies.
</Callout>

## The Saturday

This Saturday I had three bugs open on the side project. None of them was urgent. Each bug sat in a different layer of the stack: one in an OAuth reconnect, one in the database pool, one in a piece of UI navigation. Genuinely independent. But they were each annoying enough that I wanted them gone.

I opened three worktrees and started three Claude sessions, one per bug. The sessions ran in parallel for most of the afternoon.

Three trees. Three branches. Three agents, each one editing only its own checkout. None of them could stash on top of another. None of them could switch the main repo's branch out from under me. None of them could cd somewhere they shouldn't.

By the end of the afternoon I had merged three PRs. Roughly:

- An OAuth reconnect was redirecting before its bootstrap finished, so state arrived partial. The fix moved the await.
- A pooled DB connection was getting exhausted under realistic load and throwing `P2037`.<Sidenote>`P2037` is Prisma's "Too many database connections opened" error.</Sidenote> The fix capped the per-instance pool size.
- A stale UI banner was triggering a navigation into an empty view. The fix bootstrapped the right state before the redirect.

## When the first pass isn't enough

Worktrees solve collisions between agents. They don't solve incomplete fixes from any single one.

One of the three worktrees had a Storybook story that broke on push because the test setup didn't mock everything the component imported. The first attempt mocked `@/lib/analytics` and called it done. The story still failed in CI. The agent had only mocked the import it could see; it hadn't walked the dependency tree to find that the same component also pulled in a server action that pulled in `next/server`. So the suite kept failing on a different import each time, and the fix came in three separate commits:

<CodeBlock filename="git log --oneline">
```
7c22818 test(storybook): mock taskActions to break next/server import chain
fb7b925 docs(storybook): note why @/lib/analytics is mocked
026f614 test(storybook): mock @/lib/analytics in storybook vitest setup
```
</CodeBlock>

Three commits for one fix. The pattern is the same one [I wrote about last month with CSS](/blog/tests-gave-me-control/): the agent patches the visible surface and stops. The adjacent surfaces (other imports, other themes, other breakpoints) only surface when you actually run the thing in the environment that fails. Worktrees gave me parallelism. They did not give me a smarter first pass.

Played back as an [agent loop](/learn/agentic-systems/agent-loop/), the expensive part of that session is obvious. The edits took minutes each. The observe steps (push, wait for CI, read the new failure) were the afternoon:

Acting is cheap. Observing is what [fills the context window](/learn/agentic-systems/context-engineering/), and a session that burns it on two CI round-trips is a session that starts forgetting why it made the first edit. That's the real price of a first pass that doesn't walk the dependency tree.

<Callout type="tip" title="The cheap rule that prevents this">
Before declaring a Storybook fix done, ask the agent to enumerate every import the changed story's component touches and confirm each is either real-or-mocked. Same idea for any test setup. The "what else does this thing transitively need" question costs five seconds; the alternative is two CI cycles per fix.
</Callout>

## What I wrote down

After all of this I added three lines to my `CLAUDE.md` for projects where I might run parallel sessions. They're the rules I broke at least once.

<CodeBlock filename="CLAUDE.md">
```markdown
## Worktree Discipline
- When working in a git worktree, NEVER switch branches in the main repo or stash changes there.
- Stay confined to the worktree directory for all file operations.
- After pushing from a worktree, do not checkout other branches that could disrupt a parallel dev server.
```
</CodeBlock>

The first line is the one that costs you the most when violated. If an agent stashes in the main repo while you're running a dev server off that repo, your in-progress work disappears into a stash entry you didn't know existed. I've already lost eight of ten files to a stash once, and that was one I asked for myself ([the story is in the tests post](/blog/tests-gave-me-control/)). I don't need an agent doing it behind my back.

Claude Code now enforces most of the first two lines on its own, in any session started with `--worktree` or moved into a worktree with `EnterWorktree`. The docs name the gap: a shell command like `cp`, or a plain redirect, that writes into the main checkout without running git there isn't refused. The third line is still on you.

<Collapsible title="The thing I almost forgot to say">
In my setup, `.claude/worktrees/` didn't retrigger the compile loop. Don't read that as a guarantee. Gitignoring the path keeps worktrees out of your commits, and that's all it does: whether a hidden folder gets watched depends on your dev server's watcher config. If yours loops, add the path to the watcher's ignore list or move worktrees to a sibling directory. Otherwise you'll either commit a worktree into your repo (embarrassing) or trigger an infinite compile loop (humbling). Both are doable.
</Collapsible>

## What worktrees don't solve

I picked Saturday's three bugs because they sat in three different layers of the stack. That wasn't strategy. It was the queue. If I'd had three bugs that all touched the same hook, or three changes that each modified a shared type, the worktrees would have kept the diffs apart and the merge would have been a war. Physical isolation doesn't buy semantic isolation.

This shows up everywhere once you start looking. Three agents bumping the same package to three different versions. Three migrations against the same table. Three refactors of a shared internal API. Each PR individually correct, together a broken build. Worktrees give you the *ability* to parallelize. They don't give you the *judgment* to know which work can safely parallelize.

That judgment fits in four questions. Here's the version I now run in my head before opening a second terminal:

The other thing worktrees don't isolate: shared runtime resources. Three dev servers want port 3000. Three Prisma clients regenerate the same generated files. Three sets of migrations want to run against the same database. Three `npm install` calls fight over the same `node_modules`. Worktrees give each agent its own files, and the port and the database stay shared. For anything beyond filesystem state (sockets, processes, caches, shared services), you still need to think about it explicitly.

Parallelism also moves where your time goes. Saturday afternoon I wasn't typing code. I was reading three diffs, integrating three branches, and looking for invisible coupling between them. The agents worked in parallel. The reviewer didn't. If the bottleneck used to be writing code, the bottleneck now is reading it.

So "three agents do the work of three engineers" is the wrong story. Three agents did the work of three typists, and one engineer still had to integrate them.

## The real constraint

This whole post is a sequel to [one I wrote a couple of weeks ago about tests](/blog/tests-gave-me-control/). The argument there was that delegating to AI is only safe when there's a feedback loop fast enough to catch its mistakes. Tests are that loop on the *what* axis: did the change do the thing.

Worktrees are the same idea on the *where* axis. They let me trust that an agent's mistakes stay in the branch and the directory I gave it. The filesystem enforces that, so I don't have to count on the agent's good intentions.

<PullQuote>
Tests gave me control over what the agent writes. Worktrees gave me control over where it writes.
</PullQuote>

There's a third axis past those two: what every parallel agent believes about the system around it. The contracts, the shared types, the schemas, the conventions. Keeping that coherent when each session only sees the slice you handed it is the deeper problem. I haven't solved it. The [multi-agent module of my agentic-systems wiki](/learn/agentic-systems/multi-agent/) gets closest with one rule: parallelize reads, serialize writes, because agents that write shared state can't see each other's implicit decisions. Saturday got away with three parallel writes because they shared no contract, and that's the check the decision tree above runs.

If you've been running one Claude session at a time and wondering whether two would be reckless, the answer is: not if each one has its own tree. Recklessness is sharing the tree.
